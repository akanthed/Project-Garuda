# Garuda — Model Card & Responsible AI Statement

**Project:** Garuda — Karnataka Police Intelligence Dashboard (KSP Datathon 2026, Challenge 02)
**Last updated:** 2026-08-20
**Scope of this document:** every predictive/statistical model shipped in `backend/main.py` — the case risk classifier, the hotspot forecast model, and the network/community analytics. It does **not** cover the QuickML/rules request planner, which is a tool-selection system, not a predictive model (see "Agentic AI" section below for its own evaluation).

This card follows the spirit of Google's Model Cards for Model Reporting (Mitchell et al., 2019) and is written for two audiences: the judging panel, and any officer who will actually see a Garuda score on a case.

---

## 1. Intended use

Garuda is a **decision-support prototype**. Every score, ranking, or forecast it produces is:
- An **input to human review**, never an automated decision.
- Advisory — it does not lodge FIRs, assign officers, dispatch patrols, or take any enforcement action.
- Built entirely on **synthetic data** (see §2). No real case, accused, or victim records were used at any point in this project.

### Prohibited uses
- Do **not** use the risk classifier, hotspot forecast, or kingpin ranking as the sole basis for arrest, surveillance, patrol reduction, or resource denial decisions.
- Do **not** deploy any component of this prototype against real case data without: (a) revalidating every metric in this document against real data, (b) a fresh bias audit (§4) on the real distribution, and (c) sign-off from a data protection/legal review under the DPDP Act 2023 (§6).
- Do **not** treat "predicted lead" (link prediction, §3.3) output as evidence. It is explicitly labelled a statistical association in every API response that returns it.

## 2. Data

| Property | Value |
|---|---|
| Source | 100% synthetic, generated by `backend/generate_data.py` / `scale_data.py` / `generate_statewide_data.py` |
| Volume | 124,000 cases · 217,167 accused records · 152,139 arrests, across 9 Karnataka districts (`backend/data/scale_manifest.json`) |
| Real-world provenance | **None.** Names are Faker-generated (`en_IN` locale). Coordinates are sampled within real district bounding boxes but do not correspond to real incidents. Crime-type/gravity distributions are hand-authored, not derived from real KSP records. |
| Known data artifact | The repeat-offender name pool used by the generator is shared **statewide**, not per-locality — this produces a small number of unrealistically large "communities" in the network analysis (up to 355 members). This is flagged automatically as `likely_synthetic_artifact: true` in `/api/network/communities` rather than hidden. See Phase 3 notes. |
| Demographic fields present in source data | `AgeYear`, `GenderID` (on the `Accused` table) |
| Demographic fields used as model input | **None** — confirmed by inspection of `_risk_features()` in `backend/main.py`: the risk classifier's 8 features are `gravity_level, repeat_accused_count, accused_count, arrest_count, arrest_rate_percent, station_case_volume, crime_type_volume, days_since_latest`. Age and gender are stored but never read by any scoring function in this codebase. |

## 3. Models

### 3.1 Case risk classifier (`GET /api/risk/{case_master_id}`)
- **Two code paths**, both returning the same shape; the deployed response's `source` field tells you which one actually ran — that is the only trustworthy signal, not this document:
  - `zia_automl` — Zoho Zia AutoML, model id configured via `ZIA_RISK_MODEL_ID`. Requires the model to be trained in the Catalyst Console; not independently benchmarked in this document because we cannot inspect its internals from application code.
  - `local_fallback` — a transparent, auditable linear scoring rule (`_local_risk_prediction`): `score = gravity×3.0 + min(accused_count,4)×0.8 + min(repeat_accused_count,4)×1.3 − min(arrest_rate%,100)×0.006`, thresholded into low/medium/high at 10/14. Every weight and threshold is visible in this repository — there is no hidden model behind this path.
- **Metrics:** this is a rule-based classifier, not a trained model — there is no held-out accuracy figure to report because there is no ground-truth "actually a repeat offender" label in synthetic data. Its transparency (§3.1 formula above) is the responsible-AI property that substitutes for a benchmark: an officer can recompute the score by hand from the case's own numbers.
- **Bias audit:** see §4.

### 3.2 Hotspot forecast (`GET /api/hotspots/forecast`)
- **Deployed model:** `linear_trend` (per-station `numpy.polyfit` over monthly incident counts).
- **This was chosen by measurement, not default.** A rolling-origin backtest (`GET /api/hotspots/forecast/backtest`, 6 held-out months, 164 stations) compared it against naive, seasonal-naive, and EWMA baselines:

  | Model | MAE | MAPE | PAI | PEI |
  |---|---|---|---|---|
  | **linear_trend (deployed)** | **2.99** | **29.4%** | 1.31 | 0.79 |
  | ewma | 3.10 | 30.1% | 1.33 | 0.80 |
  | seasonal_naive | 4.04 | 38.0% | 1.35 | 0.82 |
  | naive | 4.11 | 38.1% | 1.32 | 0.80 |

  PAI (Prediction Accuracy Index) and PEI (Predictive Efficiency Index) are the standard hotspot-prediction metrics from the criminology literature (Chainey, Tompson & Uhlig, 2008), adapted here from a spatial grid to station units (see `_backtest_forecast_models()` docstring for the exact adaptation).
- **Decision:** linear_trend beats every simpler baseline by a real margin, so gradient boosting / any heavier model was deliberately **not** added — see the plan note "upgrade only if it beats baselines." Adding one would also have required vendoring new ML wheels for the AppSail deployment, an infra cost not justified by the backtest.
- **Confidence interval:** each forecast now returns a `confidence_interval` derived from one-step-ahead in-sample residual std (`_residual_std()`), and `training_window_months` so the reader can see how much history backs a given station's number.
- **Feedback-loop risk:** predicted hotspots can influence patrol allocation, which can change where future crime is recorded — a genuine feedback loop. Mitigation: predictions are advisory only, never automated dispatch, and this backtest should be periodically rerun against realized outcomes as new data arrives.

### 3.3 Network analytics (`/api/network/kingpins`, `/communities`, `/path`, `/predict-links`)
- **Kingpin ranking:** `0.4×degree + 0.35×betweenness + 0.25×eigenvector` centrality over a suspect-suspect co-offender graph (5,000 nodes / 6,820 edges on this dataset). Betweenness is sampled (k=300, seed=42) above 300 nodes — exact computation took 92.6s on this graph, sampled takes ~5s; this is disclosed as an approximation, not exact.
- **Syndicate detection:** greedy modularity communities (networkx built-in). Cohesion (internal edge density) and a `likely_synthetic_artifact` flag are returned per community so a reviewer can distinguish a real, tight-knit group from a data-generation artifact (§2).
- **Link prediction:** Adamic-Adar coefficient over the top-300-by-degree suspects. Every result is labelled `"label": "predicted_lead"` with an explicit advisory string — **this is a statistical association, never asserted as a real-world connection.**
- **Connection path:** exact shortest path (`networkx.shortest_path`) with every hop backed by a real shared case, date, and station — this one is not probabilistic, it is a direct graph traversal over recorded co-accused relationships.

## 4. Bias / fairness audit

Computed by `backend/bias_audit.py`, run against the full 124,000-case dataset on 2026-08-20. Report: `backend/data/bias_audit_report.json`.

**Method:** the risk classifier's exact scoring formula (§3.1) is vectorized and applied to every case, grouped by district. Any district whose "high" flag rate deviates more than 1.3× (or less than 1/1.3×) from the statewide average is flagged for review. This is a **distributional check, not a causal explanation** — a flag means "review this district's data and context," not "the model is wrong here."

| District | Cases | High-risk flag rate | Anomaly-flagged stations | Deviation flag |
|---|---|---|---|---|
| Bengaluru Urban | 100,000 | 32.03% | 4.0% | none |
| Mysuru | 3,000 | 32.63% | 0.0% | none |
| Dakshina Kannada | 3,000 | 30.80% | 0.0% | none |
| Belagavi | 3,000 | 32.03% | 0.0% | none |
| Kalaburagi | 3,000 | 33.27% | 0.0% | none |
| Ballari | 3,000 | 31.63% | 0.0% | none |
| Tumakuru | 3,000 | 31.63% | 0.0% | none |
| Dharwad | 3,000 | 31.80% | 25.0% | none (flag-rate check; anomaly rate is a separate signal, noted below) |
| Udupi | 3,000 | 32.93% | 0.0% | none |

**Statewide high-risk flag rate: 32.04%.** Every district falls within 30.8%–33.3% — no district crossed the 1.3× deviation threshold on the risk classifier. This is an expected, honest result: the synthetic generator uses the same crime-type/gravity distribution for every district, so there is no district-level bias baked into the source data for this check to find.

**One real signal worth noting:** Dharwad shows 25% of its 8 stations anomaly-flagged (2 stations) versus 0% almost everywhere else and 4% in Bengaluru Urban (4 of 100 stations). This is the time-series anomaly detector (z-score vs trailing history), not the risk classifier, and with only 8 stations in Dharwad a single flagged station moves the rate a lot — reported as-is rather than smoothed over, and worth re-checking once real data is available.

**Limitation of this audit:** synthetic data by construction has no real socio-economic or enforcement-history disparities to detect. **This audit must be re-run against real data before any real deployment decision**, and its 1.3× threshold and methodology should be reviewed by a statistician/criminologist at that point, not treated as a validated fairness bar.

## 6. DPDP Act 2023 alignment

This is a prototype using synthetic data, so most DPDP obligations do not yet apply — this section documents the **posture required before any real-data pilot**, not a compliance certification.

- **Lawful purpose & data minimisation (§4, §6):** the risk classifier's 8 features are the minimum needed for its stated purpose (triage support); no attribute is collected "in case it's useful."
- **No demographic profiling:** age and gender exist in the schema but are never read by any scoring function (§2) — verified by code inspection, not just policy.
- **Purpose limitation:** a real pilot would need an explicit data-sharing agreement scoping Garuda to investigation support only, not repurposed for e.g. HR or non-crime administrative decisions.
- **Security of processing (§8(5)):** session tokens are HMAC-signed with a mandatory non-default secret (enforced at Catalyst startup), rate-limited, and every agent/network endpoint is permission-gated — see the security hardening notes in repo memory.
- **Data principal rights & grievance redressal:** not applicable to synthetic data; a real pilot needs a defined process before onboarding real case data, which is outside this prototype's scope.
- **Retention:** synthetic data has no retention obligation; a real deployment needs a retention/deletion policy aligned to CrPC/BNSS case-record rules, to be defined with KSP legal counsel.
- **Human oversight (spirit of §16, children's data, and general due-process principles):** every prediction in this system carries an explicit "for supervisor review, not an enforcement decision" advisory string in its API response — this is enforced in code, not just in this document.

**Bottom line:** this prototype is designed so that adopting it for real data mainly requires a governance and data-sharing process, not a rebuild — no demographic profiling exists to remove, and provenance/limitation disclosures are already wired into the API layer rather than left to documentation alone.

## 7. Limitations summary (read this before the demo Q&A)

1. All metrics in §3–§5 are measured on **synthetic** data. They demonstrate methodology, not real-world accuracy.
2. The risk classifier's `local_fallback` path is a transparent rule, not a trained model — that is a deliberate transparency choice, not a placeholder for "real AI."
3. Network communities can contain a data-generation artifact (large, low-cohesion groups) — flagged automatically, not filtered silently.
4. Link prediction and kingpin ranking are statistical, not evidentiary — every relevant API response says so explicitly.
5. The bias audit (§4) found no disparity **on synthetic data with no real disparity to find** — it must be re-run on real data, with real statistical review, before it means anything for a real deployment decision.
6. QuickML (the LLM planner) is not configured in this deployment environment as of this writing; the deterministic rules planner is the only agentic path currently verifiable end-to-end.
